The Home for the Elderly system manages people, proposals, stays, and invoices. The home is organised into departments, each of which contains rooms. Each room belongs to a category type (such as RH, SF, or RNH) and has a price, and each room contains one or more numbered beds.

When a person is created in the system, they must be given a non-empty name and a non-empty birthdate. The birthdate must not be in the future relative to the current system date. The person receives a unique non-empty identifier and a registration date equal to the current system date at the moment of creation. The person's abilities are initially recorded as an empty string. A person's abilities can be updated at any time to any string value, including an empty string. The person must exist in the system for their abilities to be updated.

A proposal links a specific bed to a specific person. When a proposal is created, both the bed and the person must be specified and must already exist in the system; providing an empty bed or an empty person is not permitted. A newly created proposal has a status of "waiting" and a validated value of false. A proposal's status can be updated to one of four values: waiting, accepted, refused, or invalidated. The status must not be empty and must be exactly one of those four values. A proposal's validated flag can be updated independently to either true or false in any combination. A proposal's associated bed can be reassigned to a different bed, provided that bed exists in the system; doing so replaces the old bed association with the new one. A proposal's associated person can similarly be reassigned to a different person, provided that person exists. Attempting to update a proposal that does not exist in the system raises an error.

A stay links a person to a specific bed and records an intake date and an optional end date. A stay can only be created for a person if a proposal already exists for that person; attempting to create a stay for a person without any proposal raises an error. The bed specified for the stay does not need to be the same bed as the one in the proposal. When creating a stay, both the person and the bed must be specified and must exist in the system. The intake date must be on or after the current system date; a past intake date is not permitted. A newly created stay has an empty end date. A stay's intake date can be updated, but the new value must not be empty and must be on or after the current system date. A stay's end date can be updated to any value, including an empty value or a date in the past. Attempting to update a stay that does not exist raises an error.

Invoices are associated with a person and a date. An invoice has an outstanding amount and a status of either "active" or "paid". The outstanding amount of an active invoice can be updated to any value. If the outstanding amount is updated to zero or to a negative value, the invoice's status is automatically set to "paid". A paid invoice cannot have its outstanding amount updated; attempting to do so raises an error. Attempting to update an invoice that does not exist raises an error.
