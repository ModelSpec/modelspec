Symboleo is a formal contract specification language developed by Contract Specification and Modelling (CSM) Lab at University of Ottawa EECS department. The language aims to enable normative monitoring of smart contracts. Smart contracts are contracts that can monitor their performance (execution). They are a Cyber Physical System (CPS) that utilizes immutable ledgers (such as Distributed Ledger Technology (DLT) Platforms, a.k.a. blockchains).
A contract specification in Symboleo has two main sections: a Domain section and a Contract Body section. In the the domain section, you will be defining the data-model of the elements that are related to the (business) domain of the contract template you wish to specify. Some basic and ontological concepts are predefined in the language. Every other concept that is defined in the domain model is an extension of the pre-defined concepts. Note: Symboleo supports both time points and intervals. Since there is a one-to-one correspondence between events and time-points, and situations and time intervals; they can be used interchangeably.
The system manages **Contracts**, each uniquely identified by an ID. A Contract maintains both a status and an active status attribute. The contract status can be one of the following values: `"Form"`, `"Active"`, `"SuccessfulTermination"`, or `"UnsuccessfulTermination"`. When a contract is in the Active status, it also has an active status, which can be `"InEffect"`, `"Suspension"`, `"Unassign"`, or `"Rescission"`. The contract status follows a strict lifecycle: it can transition from Form to Active, and from Active to either SuccessfulTermination or UnsuccessfulTermination. Any attempt to transition a contract status in a different order, such as from Form directly to a termination state, from a termination state back to an earlier state, or between the two termination states, results in an error indicating an invalid status transition. Additionally, a contract cannot transition from Active status to a termination state when its active status is Suspension, Unassign, or Rescission; such attempts raise an error indicating that status cannot be changed while the contract has that particular active status.
The contract's active status can only be set when the contract status is Active. When a contract is in any other status (Form, SuccessfulTermination, or UnsuccessfulTermination), attempting to set the active status raises an error indicating that the active status cannot be set for that contract status. When the contract status is Active, specific transitions are permitted between active statuses: from InEffect to Suspension, Unassign, or Rescission; from Suspension back to InEffect; and from Unassign back to InEffect. Attempts to perform active status transitions in any other order will raise an error indicating the invalid active status transition from the current active status to the requested new active status. When the active status is Null (which occurs when the contract is not in Active status), it remains Null and cannot be changed, any attempt to do so raises an error indicating that the active status cannot be set when the contract is not Active.
The system also manages **Obligations**, each identified by a unique name. An Obligation maintains both a status and an active status attribute. The obligation status can be one of the following values: `"Start"`, `"Create"`, `"Active"`, `"Violation"`, `"Discharge"`, `"Fulfillment"`, or `"UnsuccessfulTermination"`. When an obligation is in the Active status, it has an active status that can be either `"InEffect"` or `"Suspension"`. The obligation status follows a defined lifecycle with specific permitted transitions: from Start to either Create or Active, from Create to either Active or Discharge, and from Active to Violation, Discharge, Fulfillment, or UnsuccessfulTermination. When transitioning to the Active status from any other status, the active status automatically becomes InEffect. All other status transitions, including transitioning from Active to other status, leave the active status as Null. Terminal states (Violation, Discharge, Fulfillment, and UnsuccessfulTermination) cannot transition to any other status. Any attempt to transition an obligation status in a manner not permitted by these rules results in an error indicating an invalid status transition from the current status to the requested new status.
The obligation's active status can only be set when the obligation status is Active. When an obligation is in any other status (Start, Create, Violation, Discharge, Fulfillment, or UnsuccessfulTermination), attempting to set the active status raises an error indicating that the active status cannot be set when the obligation has that particular status. When the obligation status is Active, the active status can transition from InEffect to Suspension and from Suspension back to InEffect. Furthermore, when an obligation is suspended (has an active status of Suspension), it cannot transition from Active status to Violation, Discharge, or Fulfillment; such attempts raise an error indicating that the status cannot be changed while the obligation is suspended. However, an obligation with active status Suspension can transition to UnsuccessfulTermination.
The system also manages **Powers**, each identified by a unique name. A Power maintains both a status and an active status attribute. The power status can be one of the following values: `"Start"`, `"Create"`, `"Active"`, `"SuccessfulTermination"`, or `"UnsuccessfulTermination"`. When a power is in the Active status, it has an active status that can be either `"InEffect"` or `"Suspension"`. The power status follows a defined lifecycle with specific permitted transitions: from Start to either Create or Active, from Create to either Active or UnsuccessfulTermination, and from Active to either SuccessfulTermination or UnsuccessfulTermination. When transitioning from Start to Active or from Create to Active, the active status automatically becomes InEffect. All other status transitions, including transitioning from Active to other status, leave the active status as Null. Terminal states (SuccessfulTermination and UnsuccessfulTermination) cannot transition to any other status. Any attempt to transition a power status in a manner not permitted by these rules results in an error indicating an invalid status transition from the current status to the requested new status.
The power's active status can only be set when the power status is Active. When a power is in any other status (Start, Create, SuccessfulTermination, or UnsuccessfulTermination), attempting to set the active status raises an error indicating that the active status cannot be set when the power has that particular status. When the power status is Active, the active status can transition from InEffect to Suspension and from Suspension back to InEffect. Furthermore, when a power is suspended (has an active status of Suspension), it cannot transition from Active status to either SuccessfulTermination or UnsuccessfulTermination; such attempts raise an error indicating that the status cannot be changed while the power is suspended.
