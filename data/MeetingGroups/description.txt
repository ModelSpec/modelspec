The Meeting Groups system is a platform for managing social meeting groups, their events, memberships, and subscriptions. The system consists of four main subsystems: UserAccess, Administration, Meetings, and Payments, which work together to provide a complete solution for organizing and managing meeting groups and their activities.
Users can register in the system by creating a **UserRegistration** with a unique login, email address, first name, last name, and full name. The login and all name fields must not be empty. The email must contain exactly one "@" character, must have a "." character after the "@" character, and must not end with a "." character. Upon creation, a user registration is automatically assigned a unique ID, has its status set to `"WaitingForConfirmation"`, and records the current date as the register date, with the confirmed date initially set to null. User registrations that are waiting for confirmation can be updated to modify their login, email, or name information. A user registration can transition to `"Confirmed"` status, at which point a corresponding **User** (Member) is created with the same id and other information, the confirmed date is set to the current date, and the user registration can no longer be modified. A user registration can also transition to `"Expired"` status, after which it can no longer be updated. Attempting to update a confirmed or expired user registration results in an error indicating that such registrations cannot be updated.
The system manages **Members**, which are users who have completed the registration process. Members can subscribe to the platform through **Subscriptions**. A subscription has a country code (matching the member's country), an expiration date, a subscription period, and a status. The subscription period can be either `"Month"` (valid until the end of the current month) or `"HalfYear"` (valid for six months from the current date). When a **SubscriptionPayment** is created for a member without an existing subscription, it automatically creates an active subscription for that member with an expiration date calculated based on the subscription period. The subscription payment records the payer (member), country code, value, currency, subscription period, and has a status of `"WaitingForPayment"`. The value must be positive (greater than zero), and the currency and subscription period must not be empty. A member cannot create a subscription payment if they already have a subscription, regardless of whether that subscription is active or expired. Once a member has a subscription, they can create **SubscriptionRenewalPayments** to renew their subscription. Multiple renewal payments can be created for the same member. However, renewal payments can only be created for members with an active subscription; attempting to create a renewal payment for a member without a subscription or with an expired subscription results in an error. Renewal payments follow the same validation rules as subscription payments: the value must be positive, and the currency must not be empty.
Members with an active subscription can propose new meeting groups by creating a **MeetingGroupProposal**. Each proposal includes a name, description, city, and country code, all of which must not be empty. The country code must be either 2 or 3 characters long. When created, a proposal is automatically assigned a unique ID, has its status set to `"ToVerify"`, records the current date as the proposal date, and is associated with the proposing member. A member must have an active subscription to create a meeting group proposal; members without active subscriptions receive an error when attempting to create proposals. Furthermore, a subscription can cover a maximum of 3 meeting groups (including both existing meeting groups where the member is the organizer and pending proposals). Attempting to create a proposal that would exceed this limit results in an error indicating that a maximum of 3 meeting groups can be covered by a subscription.
An **Administrator** can create a **MeetingGroupProposalDecision** for a proposal that is in `"ToVerify"` status. The decision has a code that can be either `"Accept"` or `"Reject"`, and records the decision date as the current date. When a proposal is accepted, the proposal status changes to `"Verified"`, a new **MeetingGroup** is created with the id and information from the proposal, setting the creator as the proposing member, and setting the created date to the current date, and a **MeetingGroupMember** is automatically created for the proposing member with the role `"Organizer"`, joined date set to the current date, and active status set to true. When a proposal is rejected, the decision must include a reject reason, and the proposal status changes to `"Rejected"` without creating a meeting group. A proposal can only be accepted if the proposing member still has an active subscription at the time of the decision and if accepting the proposal would not cause the member to exceed the limit of 3 meeting groups covered by their subscription. If either condition is not met, an error is raised, and the decision is not recorded.
Members can be added to existing **MeetingGroups**. When a member is added to a meeting group, a **MeetingGroupMember** entry is created with the current date as the joined date, the role set to `"Member"`, and active status set to true. A member can only be added to a meeting group once; attempting to add a member who is already part of the meeting group results in an error. The member and meeting group must both exist; otherwise, appropriate errors are raised.
Members can also create **Meetings**. Each meeting has a title, description, location (consisting of name, address, city, and country code), a term (with start and end dates), an RSVP term (with start and end dates), and limits (attendees limit and guests limit). All fields must not be empty, the country code must be either 2 or 3 characters long, the start date must be before or equal to the end date, the RSVP start date must be before or equal to the RSVP end date, and both limits must be greater than zero. When created, a meeting is automatically assigned a unique ID that does not conflict with existing meeting IDs. Only the creator of a meeting can edit it. When editing a meeting, all the same validation rules apply as when creating a meeting. Members who are not the creator of the meeting receive an error when attempting to edit it.
Members can be added to a **Meeting** as attendees. When a member is added to a meeting, if the meeting has not yet reached its attendees limit, a **MeetingAttendee** entry is created with the member, the meeting, an initial guest number of 0, the role `"Attendee"`, and the current date as the decision date. If the meeting has already reached its attendees limit, the member is instead added to the **MeetingWaitlist** with the current date as the sign-up date. A member can only be added to a meeting once; if the member is already an attendee, on the waitlist, or marked as a not-attendee (has declined the meeting), attempting to add them again results in an error indicating that the member is already part of the meeting. Both the member and the meeting must exist; otherwise, appropriate errors are raised.
A member who is an attendee of a meeting can add guests to their attendance by specifying a guest number. The guest number must be zero or positive; negative values result in an error. The guest number cannot exceed the meeting's guests limit; attempting to set a guest number that exceeds the limit results in an error. The member must be an attendee of the meeting; non-attendees who attempt to add guests receive an error. Both the member and the meeting must exist for this operation to succeed.
